# Running the reference architecture with community projects

**November 25, 2026.** A team building a new private AI service can start with OKD to retain OpenShift conventions, or start with Kubernetes and select its own ingress, identity, storage, build and monitoring tools. For an existing service, the expensive part is usually recovering data and reproducing operational behavior on the second platform. Use the pilot below to qualify a proposed target.

## What “OKE vs OCP” and “AWX vs AAP” mean

**OKD** is the community distribution associated with Red Hat OpenShift. **OpenShift Kubernetes Engine (OKE)** is a Red Hat subscription offering with a subset of OpenShift Container Platform (OCP) capabilities. Oracle also uses **OKE** for its managed Kubernetes Engine. For a subscription-free community comparison, evaluate **OKD vs OCP**. For a cloud-hosted alternative, evaluate Oracle OKE separately, including its service dependencies and charges. [Red Hat on OKD](https://www.redhat.com/en/topics/containers/red-hat-openshift-okd) · [Red Hat OpenShift Kubernetes Engine](https://www.redhat.com/en/technologies/cloud-computing/openshift/kubernetes-engine) · [Oracle Kubernetes Engine](https://docs.oracle.com/en-us/iaas/Content/ContEng/Concepts/contengoverview.htm)

**AWX covers the automation controller role.** AAP deployments can also depend on a platform gateway, identity and role mappings, private automation content, execution environments and event-driven automation. Each needs an owner and a working replacement. At this review the AWX project listed 24.6.1 as its latest tagged release and described a release pause during refactoring. Before making AWX production-critical, establish how the selected release and its dependencies will receive tested security fixes and upgrades. Keeping AAP while piloting another layer is a valid outcome. [AWX project and release notice](https://github.com/ansible/awx) · [AWX release and paired operator](https://github.com/ansible/awx/releases/tag/24.6.1)

## Pick the target that matches the operating team

| Path | What can carry forward | Work the team assumes | Good first experiment |
| --- | --- | --- | --- |
| OKD with selected community operators | OpenShift-style Routes, projects and familiar cluster APIs where the chosen release serves them | Pin OS and cluster release, verify operator catalog availability, plan bare-metal installation, own upgrades, patch response and integration testing | Deploy an existing OCI image by digest. Test TLS, a private image pull, restricted execution and a persistent write after pod replacement. |
| Kubernetes with individually selected projects | OCI images, ordinary Deployments, Services, ConfigMaps, RBAC and many application tests | Replace or adapt Routes, SCCs, OAuth, service certificates, integrated registry, builds, operator lifecycle and monitoring. Rebuild storage and identity contracts. | Port a stateless service and a synthetic stateful dependency. Test ingress, UID/file permissions, persistence, network policy and telemetry. |
| Mixed transition | Keep the current data or automation plane while moving an independently testable workload | Operate two environments and identify the authoritative writer, event consumer, identity provider, backup and rollback path for each service | Run a harmless playbook against isolated inventory or serve a test model with synthetic data. Verify the production service can continue independently. |

OKD and Kubernetes have their own release schedules. Pin actual OS, cluster version, CRD versions, operator/controller releases, plugin images and digests in a tested bill of materials. Verify upstream package provenance and license or redistribution terms for images, models, drivers and automation collections. A product subscription may be paying for certified combinations, lifecycle support, vendor triage and backports. Budget platform engineering, incident coverage, test hardware, overlap storage and recovery drills when comparing total cost. [OKD documentation](https://docs.okd.io/latest/welcome/index.html) · [Kubernetes HA topology](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/ha-topology/)

## Map the job each product performs

| Product responsibility | Community candidate and conversion work | Evidence required |
| --- | --- | --- |
| OpenShift cluster lifecycle and extensions | OKD is the closest community starting point. On plain Kubernetes choose OS, CNI, DNS, API load balancer, identity, registry/build service, lifecycle tooling and cluster backup. Map SCCs to workload security settings and admission policy individually. Choose OLM only if the needed upstream bundles are available. [OKD](https://okd.io/) · [Pod Security Admission](https://kubernetes.io/docs/concepts/security/pod-security-admission/) · [OLM](https://github.com/operator-framework/operator-lifecycle-manager) | Rebuild a clean node, pull and roll back a pinned image, preserve filesystem ownership and demonstrate allowed and denied access under the intended identity. |
| Networking, certificates and monitoring | Use a controller for Gateway API or Ingress on plain Kubernetes. Preserve edge, passthrough or re-encryption semantics, streaming, callback URLs and CA rotation. MetalLB, NMState, cert-manager and Prometheus/Alertmanager cover specific responsibilities. [MetalLB](https://metallb.io/) · [NMState](https://nmstate.io/) · [cert-manager](https://cert-manager.io/docs/) · [kube-prometheus](https://github.com/prometheus-operator/kube-prometheus) | Exercise TLS renewal, a real sign-in, a streaming request, a denied connection and delivery of a synthetic alert to one intended consumer. |
| OpenShift AI | Open Data Hub (ODH) is the upstream project. Check release-specific cluster prerequisites before selecting it for OKD or Kubernetes. For a narrower stack, use KServe and the pipeline, workbench, registry and evaluation components actually needed. Map model storage, accelerator/runtime support and identity separately. [ODH project relationship](https://github.com/opendatahub-io/architecture-context/blob/main/docs/notes/architecture-diagram-requirements.md) · [ODH](https://opendatahub.io/docs/getting-started-with-open-data-hub/) · [KServe](https://kserve.github.io/website/) · [Kubeflow Pipelines](https://www.kubeflow.org/docs/components/pipelines/) | Reopen a saved notebook and artifact, execute a pipeline and serve a known model. Measure cold/warm latency, concurrent memory use, grounded retrieval and behavior when an optional worker disconnects. |
| AAP controller, execution environments and content hub | Evaluate AWX with its compatible operator for inventory, schedules, jobs and API. Rebuild execution images with ansible-builder. Use a pinned collection mirror or evaluate galaxy_ng/Pulp for private content. Recreate identity, RBAC, audit retention and credential bindings. Migrate reviewed logical definitions, issue fresh test credentials and leave schedules paused until cutover. [AWX Operator](https://docs.ansible.com/projects/awx-operator/en/latest/) · [ansible-builder](https://github.com/ansible/ansible-builder) · [galaxy_ng](https://github.com/ansible/galaxy_ng) | A scoped user syncs a project, resolves private content, runs one harmless job and retrieves its event history. A second role is denied. Rebuild the target controller from its own backup and repeat the job. |
| Event-Driven Ansible | ansible-rulebook supplies rule execution. Consider eda-server for a control plane if it meets the selected release and identity requirements. Recreate authentication, event persistence, activation restart behavior, duplicate suppression and delivery monitoring. [ansible-rulebook](https://github.com/ansible/ansible-rulebook) · [eda-server](https://github.com/ansible/eda-server) | A synthetic alert creates one isolated job. Replay, restart and expiration behave as intended. A disconnected runner produces a visible failure. |
| OpenShift Data Foundation (ODF) | Rook-managed Ceph can provide RBD block volumes, CephFS shared files and RGW object storage. If software relies on NooBaa bucket claims, policies or multi-cloud gateway behavior, qualify that API separately. Recreate credentials, storage classes, snapshots, reclaim policies and failure domains. [Rook/Ceph](https://rook.io/docs/rook/latest/Getting-Started/intro/) · [NooBaa Operator](https://github.com/noobaa/noobaa-operator) | Provision new volumes and buckets, write on one node and read on another, validate identities and hashes, restore a database and recover objects with original access boundaries. |
| OpenShift API for Data Protection (OADP) | Evaluate the OADP Operator where its platform requirements fit, or use Velero with the destination's CSI, snapshot and object-store plugins. Enable data movement or use application-native exports for portable copies. A snapshot handle tied to the old array cannot populate new hardware on its own. [OADP](https://github.com/openshift/oadp-operator) · [Velero data movement](https://velero.io/docs/main/csi-snapshot-data-movement/) | Restore from a read-only recovery source with the original storage inaccessible. Verify database consistency, file hashes, application access and measured RPO/RTO. |
| OpenShift Virtualization and VM migration | KubeVirt and CDI supply guest lifecycle and disk import. Evaluate Multus, migration networking, CPU compatibility, CSI snapshot features and guest tooling. Forklift is an option when the source and destination meet its requirements. [KubeVirt](https://kubevirt.io/user-guide/) · [CDI](https://github.com/kubevirt/containerized-data-importer) · [Multus](https://github.com/k8snetworkplumbingwg/multus-cni) · [Forklift](https://github.com/kubev2v/forklift) | Boot a copied disk with external interfaces disabled. Verify guest agent, data and reboot, then test networking and movement across compatible target hosts on an isolated network. |
| RHEL guests and base images | CentOS Stream is an upstream development stream for RHEL. Evaluate the chosen major version, ABI, kernel/driver dependencies, repositories and support lifetime. Rebuild and test application images or guest templates separately from converting the cluster node OS. [CentOS Stream](https://www.centos.org/centos-stream/) | Boot or build cleanly, apply an update, start the workload, restore its data and recover the previous artifact. |

## Rehearse before deciding

1. **Inventory the contracts.** List resources and their owning controllers, storage modes, identity mappings, external callbacks, secrets by reference, backup method, expected throughput and recovery objectives. Mark each responsibility as keep, replace, defer or retire. Installed add-ons may have no users.
2. **Build a parallel pilot.** Give it independent DNS, credentials, writable storage and inert notifications/payments. Keep test schedulers and real webhook consumers mutually exclusive. Several VMs on one host can test function. Demonstrating host-loss tolerance requires independent failure domains.
3. **Restore and run a user journey.** Use a read-only source recovery set. Compare hashes, ownership and database integrity. Sign in, upload a synthetic document, retrieve it and reopen it after restart. Record model latency, error rate and access denials. Restore the new environment from its own backup.
4. **Price the operating obligation.** Record engineering time by layer, concurrent source/target compute and storage, steady-state patch/on-call hours, backup and drill costs, and the value of support being replaced. Reuse measured pilot hours to estimate the rest. Storage, identity and automation recovery typically need more rehearsal than moving a stateless image.
5. **Decide by evidence.** Proceed only after the team has reproduced the required user journeys, a failure, an upgrade and a recovery within agreed limits. Before cutover record the last source write, freeze writers, copy the final delta, verify it, and move consumers once. Before target writes, routing can return to the intact source. After target writes, stop writers and reconcile the new data before reversing traffic. Retire the source only after an independent restore and an agreed observation period.
